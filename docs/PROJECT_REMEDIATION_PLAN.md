## 7. 已确认的问题清单

### 7.1 已修复问题

| 优先级 | 问题 | 处理结果 |
| --- | --- | --- |
| P0 | 单据状态和库存通过多次独立请求更新，可能部分成功 | 已改为数据库原子事务 |
| P0 | 超时或重复请求可能重复入库、出库 | 已增加单据行锁和库存流水幂等键 |
| P0 | 发货流程不扣库存 | 已在 `SHIPPED` 状态事务中扣库 |
| P0 | 发货单没有必填仓库 | 创建接口已强制 `warehouse_id` |
| P0 | 前端权限查询被 RLS 全拒绝 | 已改为服务端 `/api/me` |
| P1 | 刷新后会话未恢复且没有路由守卫 | 已增加初始化、监听和路由守卫 |
| P1 | 用户接口查询不存在的 `roles.slug` | 已改为查询 `roles.name` |
| P1 | 补货权限没有种子数据 | 已在迁移中补齐权限与角色映射 |
| P1 | 退货完成时可能没有入库仓库 | 退货单创建时已强制指定仓库 |

### 7.2 尚未修复问题

| 优先级 | 问题 | 影响或说明 |
| --- | --- | --- |
| P1 | 创建主单和明细仍使用多次请求及删除补偿 | 删除补偿失败时可能遗留空单，后续应改为创建事务 RPC |
| P1 | 大部分业务页面仍是占位页面 | 库存、销售、采购、发货、调拨、售后、补货、用户和设置尚未形成可操作闭环 |
| P1 | 没有自动化测试 | 无法持续证明库存事务、权限和状态机在修改后仍然正确 |
| P1 | 没有 GitHub Actions | 合并前没有类型检查、测试、构建和迁移门禁 |
| P1 | 部分收货、部分调拨尚未完整实现 | 当前事务主要处理完整完成路径 |
| P1 | 发货与销售订单数量缺少严格关联校验 | 可能重复或超量发货 |
| P2 | 商品删除仍是物理删除 | ERP 历史追溯应优先使用停用或软删除 |
| P2 | 审计日志在部分普通创建接口中仍是独立写入 | 审计写入失败不会阻止业务成功 |
| P2 | 限流使用 Serverless 进程内存 | 冷启动和多实例会绕过限流 |
| P2 | 缺少商品、仓库、重复明细等统一业务校验 | 数据库错误可能表现为模糊的 500，或产生不合理单据 |
| P2 | 金额在部分 API 中使用 JavaScript 浮点运算 | 真实账务应以数据库 `numeric` 和统一舍入规则为准 |
| P2 | 商品搜索使用字符串拼接构造 PostgREST `or` 条件 | 需要转义特殊字符并增加查询参数测试 |
| P2 | 生产构建主包过大 | 当前构建仍有大于 500 kB 的 chunk 警告，影响首屏性能 |
| P2 | `legacy` 代码与新架构同时存在 | 容易造成维护分叉和安全修复遗漏 |
| P2 | README 的“生产级”描述与实际完成度不符 | 应在核心模块和测试完成前调整项目成熟度说明 |

## 8. 建议实施顺序

1. 在测试 Supabase 环境执行第一阶段迁移并完成并发、重试和回滚验证。
2. 优先把所有“主单 + 明细”创建接口改为原子事务。
3. 实现库存、采购收货、销售和发货四个最小业务闭环。
4. 同步建立第三阶段自动化测试和 GitHub Actions，不要等全部页面完成后再补测试。
5. 再实现调拨、售后、补货和用户管理。
6. 最后集中进行性能、监控、限流和运维加固。

## 10. 完成定义

项目达到“可内部试运行”的最低条件：

- 第一阶段迁移已在目标数据库执行并验证；
